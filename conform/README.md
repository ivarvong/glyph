# conform: conformance suites and differential oracles

Dev only; the library has no dependencies. `setup.sh` fetches and builds the oracles at pinned
commits into `conform/.ext/` (git-ignored):

| oracle | pinned | role |
|---|---|---|
| [w3c/woff2-tests](https://github.com/w3c/woff2-tests) | `dd31222` | the W3C WOFF 2.0 suites, generated by their scripts |
| [google/woff2](https://github.com/google/woff2) | `fb9c337` | the reference encoder and decoder (`woff2_compress`, `woff2_decompress`) |
| fontTools (Python) | as installed | outlines, cmap, metrics (`oracle.py`, using the `Canon` pen from `ref/make_refs.py`) |
| HarfBuzz via uharfbuzz | as installed | shaping (`hb.py`) |
| [fontkit](https://github.com/foliojs/fontkit) | `2.0.4` (`conform/package.json`) | an independent pure-JS WOFF2 decoder |

## W3C WOFF 2.0 (`npm run conform`)

```
UserAgent  298/298   display exactly the fonts the suite says must display, and decode them to
                     the outlines, cmap and advances fontTools (or Google's decoder → fontTools) reads
Decoder    164/164   decode valid files; round-trips equal the original .ttf (outlines, advances, lsbs)
Format     296/296   never reject a valid file; lenient on 107 strictly-invalid ones, all metadata
                     (which must not affect rendering) plus a reserved header field and padding
Google's decoder agrees with the UserAgent expectations on 298/298.
```

How expectations are known: `expect.py` runs each generator unmodified and records the
`valid=` / `shouldDisplaySFNT=` argument of every case it writes.

What the first run found (all fixed; the failing files are in `woff2/test/w3c/`, run by `npm test`):

1. **WOFF2 hmtx transform (§5.4) was not reconstructed.** It is used by Google's encoder.
   The transformed bytes were read as a plain hmtx table, so these fonts were rejected as
   truncated (including "Valid WOFF 5–8") or decoded with wrong advances (262 vs 1536). This
   affected 15 must-display cases. Now `woff2/src/hmtx-transform.js`, which follows the
   reference decoder's rules.
2. **Block layout was not enforced.** We displayed files with extraneous or overlapping blocks
   (7 must-reject cases). We now check, as `woff2_dec.cc` does, that the compressed data,
   metadata and private data are contiguous and 4-aligned and that the file ends there.
3. **A transformed loca with the wrong declared length was accepted** (2 must-reject cases).
4. **Collections failed as `DuplicateTable`** instead of the typed `UnsupportedCollection`.

## Corpus differential (`node conform/corpus.js conform/.ext/gf-sample.txt`)

A seeded sample (seed 20261021) of 300 Google Fonts families (`google/fonts` @ `45e3d52`,
one file per family, 90 of them variable). Each font goes through Google's encoder, and the
resulting WOFF2 is decoded by glyph and compared, exactly and in canonical form, with:
- fontTools on the original .ttf
- Google's decoder → fontTools
- fontkit on the same WOFF2

Latin text is shaped by glyph and by HarfBuzz. To fetch the sample:

```
git clone --depth 1 --filter=blob:none --sparse https://github.com/google/fonts conform/.ext/gfonts
# then sparse-checkout the paths in gf-sample.txt (escape [ and ]: they are globs to git)
```

Final run, with every fix below in place:

```
decoded by glyph             300/300   (no throws, no errors)
= fontTools (original .ttf)  300/300   outlines, cmap, advances, exact in canonical form
= Google decoder → fontTools 300/300
fontkit = fontTools          240/300   in all 60 disagreements glyph matches fontTools and Google
shaping = HarfBuzz           290/290   fonts covering the texts (870 runs: Latin, ligatures,
                                       kerning, punctuation, stacked combining marks)
```

What the corpus found in glyph (all fixed, each with a test):
1. **Placement.** TrueType outlines were not placed at the hmtx side bearing (`lsb − xMin`), so
   glyphs were 1–7 units off.
2. **Legacy `kern`** was ignored.
3. **FeatureVariations** were ignored at the default instance (variable fonts).
4. **GPOS mark and cursive attachment** were skipped, and with them: grapheme clusters,
   synthesised mark classes, canonical mark ordering.

What it found in the oracles:
- **fontkit 2.0.4** applies no side-bearing placement (glyphs off by `lsb − xMin`), and inserts a
  spurious straight segment in contours that start off-curve.
- **fontTools' glyph set** skips the placement for composite glyphs. FreeType and HarfBuzz apply
  it, so `oracle.py` applies it too and says why.
